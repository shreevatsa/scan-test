# The web app: reading and correcting digitized books

A static web app for the books this repository's methods produce. It runs entirely in the browser with plain HTML, CSS and JavaScript modules, bundled PDF and OCR runtimes, and no build step. A book consists of its PDF and page documents (schema 0.2 and 0.3, [schema/README.md](../schema/README.md)), kept in the browser and saved together as a **.chaya.pdf** ("Books" below).

Agents preparing a book can use [the portable transcription skill](../skills/transcribe-chaya-book/SKILL.md). Its folder contains a general workflow, a self-contained format reference and a Python PDF packer that work independently with public PDF tools and the chosen OCR engines or models.

The workflow tabs are **Pages · Read · Export**. **Settings** holds the book's model choices, its structure rules and its types.

- **Pages** browses scans, flags and review marks. **Process pages** finds missing boxes and transcribes pages with valid boxes. Select scans by ticking cards or entering a range such as `1-50, 62`. With no selection it uses displayed undimmed pages. The spend limit applies across finding and reading. A stopped run resumes from the work it saved. **Book checks** expands the checks across pages and notes.
- **Read** displays the book, including saved work in progress, with its contents and footnotes beside the text. Double-click a passage to see it on the scan, beside the text, with a link to the page editor.
- **Export** saves the book, original PDF, text, or HTML. It also leads to the style sheet and manages the book's copy on disk.
- **Settings** chooses the region finder and transcription model, with API credentials. **Structure** holds the book's structure rules (below). **Advanced** holds the OCR language pack and the book’s types. Read-only books offer **Make an editable copy** on Pages and Settings.

**Pages.** The processing box (Select pages, Spend threshold, Process pages, Stop, Book settings) shows in full only while pages wait to be processed or a run goes; otherwise it is one line, "All pages processed · Process again…", which opens it. **Mark checked** and **Reopen review** sit beside the page selection and apply to the selected pages. Each page card shows one state: "Checked", "N to check" with the first item, or "Not processed"; a dimmed page shows none. The dim button (×, ↺) shows on hover or focus, and always on touch screens. **Next page to check**, in the page editor's check box, goes to the next page whose card says "to check".

**Mark checked** and **Reopen review** apply to the whole page and preserve personal edits. Blank and dimmed pages have no review badge. A block with uncertain transcription carries a mark beside its text. Check credentials in Settings before a paid run. The page editor opens at `#page&p=<page id>`, with `&r=` or `&u=` for a selection. Older page addresses still open it.

**Page editor.** The scan has zoom and box drawing, and each block has a type and editable text. **Check this page** gives scan findings their next action. Use **Leave out** on an area or line you have checked, and **Restore** if it belongs in the book. **Use reader order** makes the saved box order match the reading. Select a block or scan box for its type, edge continuations and printed metadata. Formatting appears while editing text. Note markers appear as `[१]`, and a typed marker becomes a note marker on leaving the text box. **Page** includes **Revert page**, suggestions and page reprocessing. **More…** opens the block's other tools and the existing grouping and links.

**Read.** The book opens with its saved grouping, numbers, labels, joins and note links. For pages awaiting structure the editor and reader use the same grouping and note rules as the batch tools, with the book's structure rules.

**One reading path (`js/reading.js`).** Everything that assembles or reads a book (Read and the Book view, the page editor's structure display, Problems and the page checks that assemble, the Book types counts, the style preview, the exports and `tools/chaya_html.mjs`) goes through the blocks form (`schema/README.md`, "Blocks (draft 0.4)"): each page document is converted with `toBlocks` (a 0.4 page is used as it is) and derived with `fromBlocks`, with `blocksContext(pages, rules)`, so the same code serves every book and no rule is tied to a book id. The conversion is lossless, so a book saved as 0.3 reads as saved (`test/reading.test.mjs` proves the assembled book, with its note links and warnings, equal on both finished books and the public fixtures); a changed rule takes effect on pages with no saved structure and, once the app stores 0.4 pages, on every page. A reading is kept per type list and is made again only when a page document, the rules, the type list or the dimmed pages change. Unit ids in a reading are generated (`g1`…), not the saved ones. Opening the Rāmāyaṇa-mañjarī's Read takes about 2 to 3 s the first time (Kale's 0.3 s); an edit in the page editor re-derives the book in about 0.3 s.

**Structure rules (Settings → Structure; `js/rules.js`).** A book's `rules` in `book.json` (`schema/README.md`, "Book rules") are shown as plain fields: the headings that start sections (one level per line, outermost first, `heading type = section type`; a new book with a `heading` and a `section` type starts with `heading = section`), the closing line type, the patterns that end a part, start a part, end a part after a given closing and mark a division, the part names (one per line, a blank line leaves a part untitled; the names are shown in parentheses as the editor's), the verse-group marker type and the marker words with the number of verses each groups. A change is saved when the field loses focus (to `book.json`, or in this browser for a book that cannot be written) and the reading is made again; a pattern that is not valid is not saved and the field says why. **Use the defaults** removes the book's rules. `node webapp/tools/chaya_rules.mjs IN OUT [--part-closing=… --part-heading=… …]` sets them from the command line. Double-click a passage to edit its block beside the scan. Older `#blocks` and `#read&view=book` bookmarks open Read, and `#blocks&p=<page id>` opens the page editor. Run `node webapp/tools/blocks_audit.mjs BOOK.chaya.pdf` to compare a rules-only reading with the saved structure.

**Dimming pages.** On Pages, a small × on each page's preview marks it not interesting: it is shown faded in every grid (↺ brings it back), and runs and moves that default to the displayed pages skip it. The page stays in the scan list and counts, while the readers and text exports leave it out. Ticking it in a stage grid includes it in a run (a typed range does not). The Pages summary counts the dimmed pages and the page filter has "Dimmed". The list is saved in `book.json` as `skipped` (page ids, in page order), so it survives a reload and a `.chaya.pdf`, and writing it makes the copy on disk be written again. A read-only book cannot dim pages. A page that should not be in the text at all is given no content (below).

**A page with no content.** A new book has every page of its PDF. A page that is not part of the book (a library's cover, a blank page, another work bound in) is kept with no regions. In the page editor, **Page ▾ → No content on this page** removes every region of the page as one editing step, with the printed lines outside the regions, unassigned regions and the region finder’s notes. It asks first when a region has text or the page has the person's edits, and undo brings the regions back while the page is open. A page with no regions has the layout "Blank page". It has nothing to transcribe or complete, so Text and Read count it as done (its badge says "No content"), and their runs and cost estimates leave it out. Read shows nothing of it, and a paragraph that goes on across it is one unit, as across any page with no unit of its type (Read, below).

The editor can draw, retype, move, split and merge boxes. Keys 1–9 assign a type to the selection. Tab and Shift+Tab move between blocks.

**Settings → Advanced → Book types** is one tree beside the selected type's card (stacked above it below 700 px). The tree (`js/type-tree.js`, drawn with connector lines) has one root per reading flow (“flow main — …”) and one for page furniture; each type is shown where it is used, with the count for that place only: at its flow's top level and inside each container that holds units of it (a type used in both appears in both, each row with its own number and a small ⇄ mark, and hovering or focusing any appearance, like selecting one, highlights all of that type's appearances). A type used nowhere appears once, muted (“unused draft type” or “unused”), at its first allowed place: under the first container in the type list that may hold it, else directly under its flow (or under page furniture); until the counts are loaded the tree shows that layout with “…”. A container always stays at that first place, with its own count. Each row is one line: a colour dot, the type name (selecting its card; the selected row is highlighted), then grey notes: “container”, “like X” (for example “like list entry”) only when how its regions are drawn differs from the name, “may contain itself”, and one count (furniture: “N on the pages”). The **Edit type list** dialog shows the same tree, where a name opens that type's edit form. There is no second list of types. A draft type (from `types/generic.json`) used on no page and in no pending proposal is shown muted as “unused draft type”, and once a page has regions **Remove unused draft types (N)** applies the type-list “remove” operation to all of them as one revision, after the usual preview; nothing is removed automatically. **How regions are drawn.** Each printed type has a class (saved as `region`) that picks the built-in rule the region finder is given for that kind of region, so it decides how finely regions are cut (one per verse with its number, one per paragraph, one per list entry, a note with its marker, …); a figure is an illustration and has no text lines. Everywhere it is shown the app says “Draw regions like: …” with a short label (`js/class-labels.js`, whose rule wording is the first sentence of the finder's rule) and shows the rule as a tooltip and a grey line under the select. A type whose class is `other` (the finder's escape class, not one a type may have) is marked “no region rule yet”, linking to the “Change how regions are drawn” operation. The card beside the tree shows its definition, containment rules, measured page coverage and six scan examples at a time. Examples from different pages appear first. Printed types show their region crops and outlines. Containers show their descendant regions on the page, with provisional grouping labelled. Opening an example selects its region in the page editor. The editor also shows the selected type’s definition and offers **Examples of this type** and **Edit type…**. Switching views retains the selected type, example batch, page, region, zoom and pane scroll positions within the open book. Grid selection, filters and scroll position are retained too. Below come **Book details** (title, description, languages, relations, inline kinds and transcription conventions, changed with **Edit book details**; the description is the one every model call uses, and the survey sends it as it is there) and **Questions to review**. The type-by-type table and the display of revision history are gone; the revision data itself stays in the book, since it migrates pages after renames and merges. Old `#types` and proposal links open the corresponding Regions view.

Unassigned model regions are hatched and have “Give it a type” controls; one of a proposed type (method 097) names it (“proposed: X”), and once that proposal has become a type it also has a one-click “Make it T”. A region where the outline step found no ink is kept and flagged so it can be checked against the scan. Typing its text clears that flag. An empty box can be deleted. The total number of boxes in which the outline step found ink is shown when reviewing a proposed layout. Review flags include uncertain or unknown types, missing order, empty regions, uncovered printed lines, overlapping regions, provisional containment problems and continuation disagreements. Two regions overlap when more than a fifth of the smaller is covered: by their outlines where both have them, so a two-line footnote beside one-line footnotes is not flagged. Continuation flags are compared across a page break only while either page's units are provisional; settled units are checked by Read's assembly. They follow assembly's rule (Read, below): a page's first region marked as continued from the previous page, or its last marked as continuing, is compared with the nearest page past pages with no region of that type in the flow and no such mark (a blank page, a plate), and a page between is not flagged. They look no further than a gap in the PDF's page numbers, a break between sample pages or a page with no document yet. **A printed line outside all regions** is described by where it is ("near the top of the page, on the left"), not by a number. Choose **Review line** to see the crop and add it as a block. Choose **Leave out** to dismiss a blemish or show-through from the check list. A dismissed line is recorded in `source.ignored_lines` and a dismissed area in `source.ignored_regions`. Both survive saving, support undo and can be restored from the editor. A rare layout is a filter and a grouping, not a flag. Text and completion flags are computed separately for their stages. A transcription’s original type-list revision is provenance. Text flags report problems that can be corrected on the page. Pages shows findings from each processing step. `node webapp/tools/flag_counts.mjs BOOK.chaya.pdf` counts the flagged pages per stage and flag kind.

“＋ Type” adds printed types and containers. A container starts with at least one child type. “New type…” in a region menu adds a printed type for immediate assignment. By type has forms for descriptions, renaming, merging, splitting, containment, flow, how regions are drawn and unused-type removal. “Edit book details” changes the title, description, languages and transcription conventions. Each operation previews its reach across model pages, saved corrections and drafts, with affected PDF pages, follow-up work and estimated model cost.

Renames update region and unit types, containment rules and the style sheet, with old names recorded as aliases. Merges require the same way of drawing regions and furniture role, or two containers. An existing target style takes precedence. Transcription is preserved. Containment changes rebuild provisional or unprotected units where needed and flag protected units for manual repair. Figure-class changes retain text in provenance and flag region discovery. Unused-type removal checks every document version and draft.

**Find regions can propose types** with the finder “GPT-6.1 Terra · reasoning off · proposes new types” (method 097, under Find regions → Change): the request also lists the pending proposed types as “not yet accepted”, and a region that fits neither a listed type nor a pending proposal may get a new proposed type (name, one-line definition, region class) instead of plain `other`. Such regions stay unassigned (hatched, with their proposed name) and are never regions of an unknown type. A new name joins the pending list with its source (finder method, the saved call as its run, page and regions); a name that matches a pending one, ignoring case and separators (`Colophon`, `colophon_line` and `colophon-line` are one name apart from `colophonline` only in spelling), is merged into it, adding the page to its evidence. Pages are processed one after another and the pending list is read when each request is built, so later pages of a run see what earlier pages proposed. Comparison trials propose nothing.

**Proposed types in the page editor.** The default region finder (method 097) may give an unassigned region a `proposed_type` it could not match to a listed type. Check this page then says “An area may be a new type, “X”” with **Add type X** (the new-type dialog filled in with the name and, from the book’s saved proposals when it has them, the definition and class; saving adds the type to the list as the next revision and gives the area that type), **Review area** and **Leave out**. When X is already in the list the button reads “Use type X”. The earlier Proposed types box and surveys of pages were taken out of the app; `work/type-proposals/pending.json` is still read for definitions and written by the region finder, and a book that holds survey proposals opens as before.

- **Page editing** shows the scan and line outlines beside the transcription.
  - It edits everything about the page but its stage: the regions (a selected region's inspector has its type, Examples of this type, Edit type…, Earlier/Later, its box (and dragging its handles on the scan), Split region, Merge regions, Recompute outlines and Delete region; **＋ Region** draws one; keys 1–9 set the selected region's type and Tab moves between regions while the caret is not in the text), the transcription (typing, the formatting buttons, ＋ Marker and a marker's printed sign, the printed page label when nothing is selected), and the structure, through the **structure panel** of the selected block: its place in the book (part, episode, group), its number, label and language, **Start a new … here**, **End the … here**, **Join with the next unit**, **Group with the next n as …** and **Remove** a group, each stored as an override on the page (`structure.js`); a marker's panel chooses its note or none. A block's continuation flags (From previous page / On next page) say whether its unit goes on across the page edge.
  - Above the page's units, the page's review flags (as the grids count them: region flags and text flags) are listed: a printed line outside all regions as a row with a crop and **Add a region** / **Ignore**, overlapping and no-ink regions, a continuation flag with "Open page N"; then "Ignored lines (N)" with Restore, unassigned regions ("Make it T" / "Give it a type") and the model's notes on the page. A region whose transcription was kept aside (its line count did not match) offers **Put it on the line pieces**. A model's suggestion waiting for the page has its Review button at the top of the inspector.
  - **Page ▾** (writable books) acts on the whole page: Review page with AI (below), No content on this page (above), **Find regions on this page again** and **Read this page again** (`js/page-actions.js`). The last two take the stage's own run path (`pipeline/batch.js`, as the Regions and Text run buttons do) for this one page, with the book's chosen finder or transcription model and the same rules: its key must have been checked in this browser (a local finder needs none), the spending check applies, costs go in the ledger, a saved model result is reused (to call afresh, use "Ignore saved model results" in the stage's run box), and a person's work is never overwritten: a protected layer gets the result as a suggestion to review. When the choice cannot run here (no checked key, or Regions set to draw by hand), the stage's grid opens with the page selected and its run box ready. Reading again needs valid scan boxes.
  - A region drawn with ＋ Region is placed where it is drawn. With a unit or a region selected, the type menu after drawing also has "into <that unit>" (unticked by default): ticked, a unit of the same type takes the region itself and a container that may hold the type takes the new unit.
  - The page document is stored in the blocks form (schema 0.4): regions and text, plus `overrides` for what the book's rules do not give; the units, flows and relations the editor shows are derived from them (`blocks-format.js`, `reading.js`). Region edits (`ops.js`) change regions only: a drawn region gets the next reading-order number; a deleted region's gap closes; a retyped region keeps its number, and page furniture has none; a figure keeps its line pieces aside and gets them back if it is given a text type again; splitting a region makes a new block right after it, relations from the moved line pieces following their text; merging joins two blocks of one type; Earlier and Later move a region among the reading order. Overrides that name a block or a unit that a region change removed are dropped, and the page's check list says "A grouping you made here no longer applies." once. Text on line pieces is kept through all of these. The edits are saved as the person's (`edits/`), with the layers they change (regions, text) marked edited. A region with no line piece shows "(no text — click to type it)": a click gives it one line piece over its outline (`ops.addLinePiece`) and puts the caret there.
  - Hovering a line highlights its outline. Zoom, fit width and fit height keep their place. Fit height is retained across pages and resizes.
  - ＋ Marker inserts a note marker at the caret; a selected marker's printed sign and its note link are set in the inspector. Line joins have explicit controls and can also be cycled at a line’s right edge.
  - Changes are checked and autosaved. Invalid edits are retained as drafts. Undo and redo cover page edits. “Revert page” returns to the latest stage save.
  - Focused saves preserve newer work in other layers. Concurrent changes to the same text or unit grouping require a fresh selection or reload.
- **Read:** the whole book as one text, assembled from its pages as `book.py assemble` does, with the user's corrections.
  - A unit open at the end of a page joins the unit of the same type open at the start of a later page of its flow when every page between has no unit of that type there and no open end of its own: a blank page, a plate (a figure, with its caption and running header), a page of other kinds of units. Their units follow the joined one, so a plate's figure comes after the paragraph it interrupts. A page between with a unit of that type, or with an open end of its own, stops the join, and the page break is a problem. The same rule holds a level down (a paragraph inside a chapter that goes on across a plate). Pages awaiting transcription are gaps that nothing joins across; Problems and Export, which assemble every page with a document, treat a page with no document yet the same way.
  - Headings, verses, paragraphs, tables and notes are shown according to their types, with formatting. Figures are shown as their part of the page image, with their label.
  - Note markers link to their notes and back.
  - The printed page number is shown where each page starts.
  - Read uses the saved reading order. A container of type `title_page` centers its statements with their printed line breaks. When the reader and saved box order disagree, the page editor's check names a pair using their visible region IDs.
  - A dimmed page (Pages, ×) is left out of the book, not a gap: a unit goes on across it, as across a duplicate scan of a page; Read, the Book view, Problems and the exports all leave it out.
  - Read shows the text without printed page numbers, beside a contents list of the parts and their sections (each by its label and number, from `chaya_sections.mjs`), which marks the part and section in view. Each note sits in the right margin beside its marker, and a note no marker points to beside the start of its page; where the margin does not fit (below 820 px) a marker opens its note under its verse or paragraph. Below 1240 px the contents open from a button. A printed table of contents (a list item "title .... page") is shown as title, dotted leader and page, the title linked to the section whose label is nearest it (on or near that page), or else to the page.
  - Units in a row stand side by side where the width allows, and one under the other where it is narrow.
  - "As printed" (for a book with a style sheet) sets each unit as the book prints it: fonts, sizes, alignment, margins, indents and spacing, from the style sheet and the units' own styles, at the book's measure.
- **Settings → Advanced → Book types** shows the book's type list, its own part of the schema (the format, `schema/schema.json`, is shared by every book).
  - the tree of what may contain what, from each flow's top level, with how many units of each type stand in each place;
  - the page furniture types;
  - a table of each type: its region class, what it may contain, its flow, language, numbering, total and description;
  - the relations, inline kinds and transcription conventions.

  Operation forms preview and apply changes. “Download types.json” gives the file, and the revision history records applied operations.
- **Read, Style sheet** the book's style sheet (schema 0.3), seen and edited:
  - the base style of all text and each type's style (font role, size, leading, weight, italic, alignment, left margin, first-line indent, space above and below), in a table where an empty cell inherits the base;
  - the font roles and their font families;
  - the page's size and text box (whose width is the measure).

  A preview of a few pages, set as printed, follows every change, and each change is checked against the schema. "Save" writes `style.json` into a book folder (and names it in `book.json`). For a read-only book, the sheet is kept in this browser over the served one, until "Back to the book's own". "Download style.json" gives the file. A book with no style sheet can start one from plain defaults. Units' and line pieces' own styles are set in the page view.
- **Read, Problems** what the checks find across the book (as method 047's `book_report.py`):
  - pages whose document fails the checks (the schema and the type list's rules, as `book.py check`), whose corrections are kept as drafts until they pass;
  - page breaks where units marked as going on do not join;
  - printed page numbers out of sequence. Pages that print no number, as a chapter's first page, are listed apart, as a note;
  - which pages the user corrected, and the transcription model's notes.
- **Export:** the book as one document of the book schema (JSON), the book as plain text with page references (a figure as `[figure: label]`), the book as one web page (HTML laid out as the Book view, with its contents, notes in the margin and a small script; as printed where the book has a style sheet, with its figures embedded; `tools/chaya_html.mjs` writes the same page from the command line, without figures), and the user's corrections as one file (and importing such a file).
- **Processing pages** makes page documents in the browser. It runs the saved region finder and transcription model when each step is needed.
  - **The recipe** (`js/recipe.js`): a new book starts with GPT-6.1 Terra regions proposing new types (method 097: 042's request with the pending proposals, and the local step), books that saved no finder keep 042, Gemini 4 Hydrogen low transcription of the whole page (below) and Gemini 4 Argon high completion, saved in its `book.json`. Books made before this keep the reader they saved; a book that saved none reads as Argon low. A type proposal's or an excerpt's model choices replace it. "Change" in a stage chooses another model for the book.
  - **Cost before a run:** each stage estimates new work from the book's own completed calls of that model (their mean cost a page). Until it has some, the recipe's models use the cost measured on a 267-page scanned book: about $0.010 a page for regions and $0.032 for completion, and, for Hydrogen's whole-page reading, 1.9 cents ($0.019) from method 100's run on the Rāmāyaṇa-mañjarī (519 calls, $9.86; Argon low's $0.038 is the measure for that model). The Pages processing box shows the reading's share ("reading about $X at $0.019 a page"). Another model without the book's own calls says it has no measured cost yet. Local models are free. The estimate after moving pages on to Read uses the same figures. The comparison views offer an editable copy of a URL book. For an excerpt with a larger cost-projection target, “Start from the full PDF with these settings” opens a new-book form carrying the current types and model choices.
  - **Making a book.** Open a plain PDF from the library to create a book from the whole PDF: every page is in it, and a page that is not part of the book is given no regions in Regions ("A page with no content", above). The form defaults to common draft types, which can be refined in Regions, and the book starts with the recipe (above). Alternatively, propose book-specific types from sample pages or supply an existing list. Browse all PDF pages as thumbnails, open larger previews and check pages to include. The sample field accepts `all`, ranges such as `1-50`, and lists such as `1, 7, 43-44`. Request a proposal from GPT-6.1 Terra with reasoning off or Gemini 4 Argon with high thinking after checking the credential. The review shows descriptions, containment rules, reading flows, links, inline kinds, transcription conventions, supporting page references and questions. Descriptions and grouping rules can be edited before approval. A model proposal must be reviewed before use. Continuing from an excerpt carries over that book's types and model choices.
  - **Unit types** start as the draft list; the type list is edited in Settings → Book types and extended by “Add type X” and Review page with AI (surveys of pages and the Proposed types box were taken out of the app; methods 095, 096 and 098 keep them). The new-book form no longer calls a model for a whole proposed list: for an excerpt of an existing book it offers that book’s types (or another list), and for a plain PDF opened with `&proposal=<url>` it shows that saved whole-list proposal (methods 077, 078, 091, 092) for review, with its evidence pages viewable under Browse all PDF pages.
  - **The source PDF:** the PDF is copied into the folder as `source.pdf`, the book's source.
  - **Page images:** each page is analyzed (its images, where they are drawn and how much of the page they cover, and its text layer's characters) and rendered with the bundled pdf.js. A scanned page (an image covering at least half of it) is rendered at 300 dpi, or at the scan's own resolution when that is lower; any other page at 300 dpi. The cap no longer applies to a digital page with a small ornament, which it used to lower to 240 dpi.
  - **What each page records:** its PDF page, its rendering, its images and its text layer's size.
  - **Regions** use the selected finder and the local step of methods 063, 093 and 094 in the worker (093 sets the weak ink threshold from the page's paper level, so grey paper no longer fails as too little text; 094 first divides the page by a smooth estimate of its local paper brightness, so a dark band along an edge no longer swallows the line ends that touch it). Models use method 042's book-specific prompt and schema. Free finders supply coarse blocks for manual review. Per-finder results are saved under `work/region-finders/<page>/<profile>.json`. Normal stage processing also writes the active `work/<page>.regions.json` and merges an editable provisional page document.
  - **Whole-page reading (method 100)** is the first reader in Settings and the default for new books: "Gemini 4 Hydrogen · low thinking · whole page" (`hydrogen-low-page`, model `gemini-4-hydrogen`, thinking low, $1.50 / $7.50 per million tokens, thinking counted as output). One call a page, with the same transport as the other Gemini readers (`generativelanguage` interactions, key header, 75 s deadline, ledger entry before sending, call record under `work/reader-calls/`). The request is one image, the page as the app draws it, and a prompt (`wholePagePrompt` in `js/pipeline/split.js`) with the book's title, description and conventions, the page's text regions in reading order (id, type, number of line pieces, box as [ymin, xmin, ymax, xmax] in thousandths) and the instruction to return each region's printed lines, exactly as many as listed, with footnote markers in square brackets. The schema is `{ regions: [{ id, lines: [string] }] }`. The answer goes through `mergeText` as the other readers' do, so `[n]` becomes a zero-width note-marker span with an id unique on the page, a person's text is not overwritten (a suggestion waits), and a result that fails the page checks is not applied. A region whose answer has another number of lines than its line pieces keeps its text and shows "the reading of this area did not fit its lines" in the page's checks; an answer that fits no region, or names an unlisted region, is an error and nothing is applied. A saved reading is reused when the page image, the regions' boxes and line pieces and the model are the same (`geometry_key`); a changed type or order alone does not make it stale, and there are no partial repairs (a changed region reads the page again). The Argon, Carbon, Flash and Flash-Lite readers still send an overview and a cut-out for each region (18,000 to 56,000 image tokens a page, against about 1,100). `gemini-4-hydrogen` is assumed to exist on the Gemini API the app calls; method 100 used it on Vertex AI.
  - **Transcription** uses the per-book choice of Hydrogen low (whole page), Argon low or high, Flash low, Flash-Lite minimal, local Tesseract, or Cloud Vision Text Detection or Document Text Detection. The other language models receive the overview and numbered region cut-outs. Tesseract and Cloud Vision map full-page word boxes to shared source-line polygons.
  - **Schema assignment** uses text-only input with Argon high or low, Flash low, Flash-Lite minimal, or Terra with reasoning off. It builds unit trees, joins, continuations and note links while the app retains the selected transcription model’s text. Argon high is the default for existing books. Transcription and schema assignment are saved independently for each model. Batches transcribe all queued pages before schema assignment, so adjacent readings are available.
  - **Retries and caching** reuse matching successful stages. Transcriptions also match by image, model and region/line polygons, so changing types, conventions or reading order reuses the reading. Older reading records gain this geometry key when used. Completion takes current corrected text, formatting and note markers, retaining the old completion fingerprint when their content is equivalent. A failed structural call can be retried without repeating transcription. The Transcription models tab also offers an explicit new structural call for a selected result.
  - **Changed-region transcription** compares the current shapes with the same model's saved reading. Only changed or added text regions need new model output. The result combines them with compatible saved regions. After a box edit, open Text, include the processed page and click “Transcribe”. Leave “Request fresh model results” unchecked to use repairs. “Review re-transcription of this page” prepares that selection from the editor. An explicit fresh request processes the whole page. A full pass is also needed when there is no compatible saved text for the scan, chosen model and OCR language.
  - **OCR repairs** reuse Cloud Vision's saved full-page word boxes when available, with no new Vision charge. Tesseract runs locally on the full page to keep word assignment consistent, then merges only the changed regions. Completion uses the full current transcription, including human corrections.
  - **Repair recovery** archives the prior reading and retains each contributing call. Completed partial responses can be reused after an interrupted save. An unresolved partial attempt requires review before an explicit fresh whole-page request. A newer cached reading is preserved when an older call finishes later.
  - **Saving stages** merges the latest page and preserves edited or accepted layers. Conflicting candidates are recorded in `source.suggestions` with their work-record paths. A valid draft participates as edited content. An invalid draft stops the model step. A journal in `work/pending-stage/` makes the model document, manifest and removal of the merged edit recoverable together. The previous protected page is retained in `work/history/`. Opening or exporting a book recovers pending saves. Comparisons and read-only books keep their trials in work records. Suggestions open in the shared review dialog.
  - The keys are kept in the browser (IndexedDB) and sent only to OpenAI and Google. Costs are estimated from returned usage, including thinking, cached input and OpenAI cache writes, at the recorded paid-tier prices. Unavailable costs are displayed explicitly and stop further calls in the batch.
  - **Processing a book** starts in Pages. Choose models and check credentials in Settings. Select pages and click **Process pages**. The run shows progress and honors a shared spend limit and stop button. Review the findings in Pages and save the updated book from Export.

Book cost projections recover original whole-page prices from reading history after region repairs. Each stage uses its available measured samples. A missing stage is named beside the dollar subtotal until a full total can be estimated. The saved API-attempt ledger includes repair and retry charges. Composite readings deduplicate contributions from a reused OCR response by its call path.

## Reviewing one page with an AI instruction

Open a page and choose **Review page with AI** in the page editor's **Page ▾** menu. Choose Terra with reasoning off or Argon with high thinking, enter an instruction, check the credential and click **Review this page**. The model receives the scan, its current region assignments, the book’s type list and the instruction. Each explicit request is a billable call with saved usage and estimated cost.

The result contains an explanation, optional printed type additions and a complete proposed region layout. Each proposed type shows “Draw regions like: …” with the model’s class kept and a small **change** control (paragraph, with a note, when the model gave none); Add is never disabled for it. **Review type additions** opens the ordinary revision preview. After the proposed types are available, **Review proposed regions** computes local outlines and opens the shared layout comparison. Applying its reviewed choice updates the page. Adding a more specific type supports retyping this page while the full type editor remains available for wider revisions.

Responses are saved with the book and restored on reopening the form. Raw calls retain the instruction, input type list, scan hash and dimensions. The call ledger can recover a response if its latest pointer failed to save. Region previews check the scan and proposed definitions before applying the normal review logic. The recipes are methods 087 and 088.

## Reviewing suggestions and model differences

A saved result held back by protected work appears as a suggestion in its stage grid, page editor and reading panel. Open it to compare current and proposed versions against the scan. Keep the current version, take the proposed version or dismiss the suggestion. Saving a choice protects the reviewed layer. A partial choice retains the suggestion for the remaining items.

For a repair using the same model as the page, the suggestion keeps current transcription in unchanged regions, including human corrections and printed-marker identities. Those regions are labelled “Current text retained”. Model comparisons continue to show the model's saved text.

Choose a whole page, one region or one text line, and correct the chosen line when needed. A grouping choice replaces the smallest complete shared subtree. Changes to ancestry, flow or linked units may require the whole page. The preview reports the number of regions affected, transcriptions becoming pending and removed links. Invalid or stale choices require a fresh review.

Reviewed text supplies checked-error scores. Completion scores use reviewed structural fields whose input and current page choices still match. Counts of model differences remain separate. Review saves and their evidence share a recovery journal, with the previous page retained in work history. Saving choices requires an editable copy of the book.

## Region finders and transcription models

Settings chooses the book’s region finder and transcription model (and, under Advanced, the OCR language pack); the choice is saved per book. The region finders are Terra, Astra low, GPT-6.1 Sol low, the four Gemini variants, local line blocks and Tesseract paragraphs. Credential checks are grouped by provider and verify access to the selected models. Free blocks are meant for manual correction: they guess only coarse classes, and map a class to a book type only when exactly one matching type exists. All local guesses are marked uncertain. Tesseract uses automatic segmentation mode 3 for layout and the selected OCR language pack, and mode 6 for transcription. Methods 079–086 kept the nine-page public benchmark and frozen runtime that compared the finders (about $1.70 for 54 calls, see NOTEBOOK.md); the comparison screens were taken out of the app, and the method folders keep their code and results.
The estimate of a whole book’s cost is the region-finding cost plus the sampled transcription and completion costs, and needs all three samples.

Completed transcriptions live in `work/readings/`, structures in `work/structures/`, immutable API attempts in `work/reader-calls/`, and checked reference lines and the cost ledger in `work/reader-lab/`. Cache fingerprints include the source image, geometry, model settings and generated prompt. Structuring additionally fingerprints its transcription, type definitions and neighboring text. For a URL book, these records are kept in IndexedDB. They are included when saving the book as a `.chaya.pdf`, together with the per-book transcription model setting. API keys stay in browser settings. A failed write after a paid response still counts its cost and stops subsequent API calls until storage is recovered.

Gemini 4 Carbon is available with low thinking through [method 089](../methods/089-gemini-4-carbon-low-reading/README.md) and high thinking through [method 090](../methods/090-gemini-4-carbon-high-reading/README.md). It uses the existing Gemini credential, with its own model check, saved results and dated prices.

Tesseract.js 6.0.1 and its English, Kannada and Sanskrit language data are bundled in `vendor/tesseract-6.0.1/`. Local transcription has zero API cost. It supplies plain text, so inline formatting and note markers need review. Page-region detection and schema assignment have API costs. The first local transcription loads and initializes the OCR runtime.

Cloud Vision Text Detection and Document Text Detection run as separate OCR options using one image and one feature per page. Their estimates use the standard $1.50 per 1,000 units before monthly free usage and volume discounts. Under API keys, choose API-key or OAuth authentication and supply the corresponding credential. OAuth may also need a Google Cloud quota project with Vision enabled and billing configured. API keys and project settings persist in the browser. OAuth access tokens stay in the current book session. The app sends credentials in request headers. Cloud Vision produces plain text, so inline formatting and note markers need review. API error responses and missing word geometry are recorded as failed stages.

## Running it

Serve the repository root and open the app, for example:

```sh
uv run --offline python -m http.server 8765 --bind 127.0.0.1      # from the repository root
open "http://127.0.0.1:8765/webapp/"
```

Then, in the library:
- **Open a PDF or a .chaya.pdf…** A plain PDF starts a new book, or opens the book this browser already has from it. A `.chaya.pdf` goes into this browser, or offers to replace the browser's copy, open it, or keep both.
- **Books in this browser:** open one, download its `.chaya.pdf`, or delete it. Each row says when its copy on disk was written, or that it has none. Below the list the browser's answer on persistent storage and the space used are shown. A folder in the browser's storage without a readable `book.json` is listed with "restore…" and "delete…".
- **Examples** (`examples.json`, `js/examples.js`): the front page lists example books, each a `.chaya.pdf` that a click loads through `?book=` as described below. A book is listed only where its file is found: `webapp/examples/<file>` on the published site, `outputs/books/<file>` in a checkout (a missing file is left out, so there is never a dead link). Private books are not listed.
- **Open a PDF by URL** (`?book=<url>`): the app fetches the PDF (with a bar and "Downloading <file>… N of M MB" as it comes, which matters for a large book over a slow link; then a bar while the book is read, and "Saving the book in this browser… N of M files" while a `.chaya.pdf`'s files are written into the browser, about 8 s for the 4,252 files of the Rāmāyaṇa-mañjarī) and opens it exactly as a PDF chosen from disk (a `.chaya.pdf` is imported as a book in this browser, with the same prompt when the browser already has it; a plain PDF starts a new book). The server must allow the fetch (same origin, or CORS), such as `http://127.0.0.1:8765/webapp/?book=../outputs/books/kale-1913.chaya.pdf`. Where the page is not served over https or from localhost, a `.chaya.pdf` opens read only instead, with corrections kept in IndexedDB.
- A plain PDF can also supply `&proposal=<url>` to preload a saved unit-type proposal. Its source PDF hash, type rules, page evidence and call metadata are checked before review. Reviewing this saved result and creating the book require no API key. The user must approve the types. Saved call records and optional transcription/schema model choices are copied into the created book. The proposal review's **Saved proposal JSON** section provides the transferable package. Locally edited proposals take priority when reopening the same PDF.

Keeping books in the browser, and the hashing that checks a `.chaya.pdf`'s original, need a secure context: `https`, or `localhost`. Served over plain `http` to another name (such as a Tailscale address), the app opens a `.chaya.pdf` read only, and says so in the library.

For access from a phone or another device on your tailnet, run `tailscale serve --bg http://127.0.0.1:8765` and open `https://<machine>.<tailnet>.ts.net/webapp/` with Tailscale connected. On macOS the CLI may be `/Applications/Tailscale.app/Contents/MacOS/Tailscale`. [Tailscale Serve](https://tailscale.com/docs/reference/tailscale-cli/serve) provides HTTPS within the tailnet. Keep the host and local server running. Browser books and API keys are separate on each device and origin, including when switching from localhost to HTTPS. Export a `.chaya.pdf` and open it in the other browser to transfer a book and its saved work.

If the page says the app could not start, a content or ad blocker has probably blocked one of its files (the browser's console names it): allow the page in the blocker. File names that blockers match, such as "pageview" or "analytics", are avoided.

The app is static, so it can also be hosted anywhere (GitHub Pages and the like); `?book=` then needs a URL the browser may fetch.

## Books

A book is a folder of files (in the browser's storage, or inside its `.chaya.pdf`; the app cannot open a folder from disk, only a `.chaya.pdf`, a PDF or a URL). The PDF is the only input format (the user's decision, 2026-11-07): page images are to be made into a PDF first, for example with img2pdf.

```
book.json     {format: "book-folder", version: 1, book_id, title, types: "types.json", style: "style.json" (optional),
               pdf: {path: "source.pdf", name, sha256, page_count},
               pages: [{id, document, label, valid, pdf_page, width, height, image (optional), source}]}
source.pdf    the book's source PDF, exactly as given
types.json    the book's type list
style.json    optional: the book's style sheet (schema 0.3), named in book.json as style
pages/        one page document per page: the model's results, never changed by the editor
edits/        the user's corrected page documents, one per corrected page (no history); page documents are 0.4 (regions and overrides); work/pre-0.4/ keeps a converted page's 0.3 structure
work/         processing records, cached readings and structures, immutable API attempts, trial references and costs
images/       page images: a cache of pages drawn from the PDF (or, in the repository's folders, their rendered images)
```

`pages` lists the book's pages in reading order: for a book made in the app, every page of its PDF. A page that is not part of the book has a page document with no regions (above), not a separate list.

**Where a book lives:**
- **In the browser** (the usual place): the origin private file system, under `books/<name>/`, in any current browser. It is saved as you work. The address carries `?local=<name>`, so a reload reopens the book. The browser is asked for persistent storage (`navigator.storage.persist()`) when a book is made, imported or opened, and its answer is shown in the library and in Export. Storage can still be cleared, so a book worth keeping needs a copy on disk (below).
- **Read only** (only where the browser keeps no books, such as plain http): a `.chaya.pdf`, with corrections kept in IndexedDB.

**The copy on disk** (`js/disk-copy.js`, Chrome and Edge): Export's "Save to a file…", or the same button in the book's header, asks once for a file with `showSaveFilePicker`. Its handle is kept in IndexedDB, and the book is written to it as a `.chaya.pdf` when a processing run or comparison finishes or stops, after review marks change or sent back, and at most every five minutes while there are changes. Leaving the book writes its last changes first. Export can write it now, choose another file or stop keeping it.
- **The header** says "Saved in this browser", and "Saved to <file name>" once a file is kept (hover for when it was last written). Once the book holds a model result or an edit and has no file, it shows "Saved in this browser" as a warning with "Save to a file…". Where the browser has no `showSaveFilePicker` (Safari, Firefox, phones), it offers "Download .chaya.pdf" instead, and the warning ends while a download has the latest change.
- **Permission:** after a reload the browser usually asks again before the app may write the file. The header then shows "Not saved to <file>: the browser needs permission again" with "Allow writing". A failed write is shown in the header with "Try again", and is retried with the next changes. Nothing is written when the book's files in the browser cannot all be read, so a damaged book never replaces a good copy.
- **Before spending:** a run that calls a paid model (stage processing, page review) waits in a dialog when no copy outside the browser has the book's latest change. The dialog offers to keep a copy on disk (or download one, or allow writing again), "Run anyway" or "Cancel". A working copy on disk never blocks a run, since it is written when the run ends.
- **A book whose files cannot be read:** opening a book in this browser first checks its source PDF and the document of every processed page (a page whose manifest entry has `valid` set). If any cannot be read, the book is not opened. The screen names each file and its error, and offers "Restore from the copy on disk", "Restore from a .chaya.pdf…" (the same book only), "Open what can be read" and the library.

**Page images:** a page is drawn from its PDF page, at exactly the `width` × `height` its regions are measured in, when it is first needed. A book in the browser keeps the drawing in `images/`; that cache is not part of the book's data. The size comes from the page's analysis when the book is made: a scanned page at 300 dpi, or the scan's own resolution when lower; any other page at 300 dpi. A page with an `image` file (the repository's folders) uses that file.

**A `.chaya.pdf`** (`js/chayapdf.js`) is the book as one file: its PDF with the book's data attached. The name is only a convention: the app recognizes a book's PDF by what is inside it, an attached `chaya.json` of format `chaya-book`, whatever the file is called.
- **What it holds:** the original PDF's bytes, unchanged, followed by one incremental update. The update attaches `chaya.json` (compressed, as an embedded file, also listed in the catalog's associated files).
- **chaya.json** is `{format: "chaya-book", version: 1, original: {name, sha256, length}, saved_at_utc, saved_by, files}`, where `files` holds the folder's files but `source.pdf` and `images/` (JSON files as objects, others as text).
- **Recovering the original:** a comment right after the original's bytes records their length and sha256, so the original is recovered exactly by cutting the file there, and checked.
- **No growth:** saving again rebuilds the update on the original, so the file does not grow.
- **The PDF's own attachments** are kept, in one flat list with `chaya.json`.
- **Viewers:** it opens as the book in any PDF viewer.
- **Encrypted PDFs** are refused.
- **Saving:** Export's "Save as .chaya.pdf" saves it once. In Chrome and Edge it saves into a chosen file; elsewhere it is a download. For a read-only book, "Save to … again" writes the same file again. A book in this browser keeps its copy on disk instead (above). Opening a `.chaya.pdf` and saving one both count as a copy outside the browser until the next change. Export also offers the source PDF alone.

**Edits:** an edited document keeps its `source` and adds `source.edited` (when, from which model result). A page whose corrections are all undone goes back to having no file in `edits/`. Versions that do not pass the checks yet are kept in the browser as drafts, and reopened with the page.

**Tools** (repository side):
- `tools/make_book_folder.py` makes a book folder from a transcription run (method 052, 054, 055 or the PDF methods' outputs). It upgrades 0.1 documents to 0.2 with `schema/inline.py`, gives each region its `box` from the region step's box, hard-links the page images, and hard-links the source PDF (`tools/add_source_pdf.py`, which also adds it to an existing folder).
- `tools/make_chaya_pdf.mjs FOLDER [OUT]` makes a folder's `.chaya.pdf`, reads it back and checks it. Each page entry gains its width and height, and drops its image.
- `tools/flag_counts.mjs BOOK.chaya.pdf [--pages]` counts the pages each stage flags, by flag kind, as the page grids do.
- `tools/chaya_baseline.mjs IN OUT` saves a baseline of a book with no problems in its units: any page whose grouping is not accepted or edited goes back to the provisional grouping (`groupingReset`, as the "Back to provisional grouping" button does), and a break marked as continuing across a page that does not join is cleared, so Read's Problems shows no page break where units do not join. The result is a plain sequence of units per page.
- `tools/chaya_sections.mjs IN OUT [--closing=TYPE] [--part-closing=PATTERN]` groups a book's units into sections without a model, from its closing lines: a unit of the closing type (`section_closing`) ends an episode, and a closing whose text matches the pattern also ends the part around its episodes. It starts at the page where the first verse stands and stops at the last closing, makes the containers open at a page edge where they go on, lets `section` contain the closing type in the type list, and checks every page and the assembly before it writes. The book's own closing after the last part stays outside the parts. `--part-heading=PATTERN` lets a heading start a part where the part before has no closing; `--part-after=PATTERN` ends a part after an episode's closing (a boundary the book does not print, recorded as inferred); `--division-closing=PATTERN` keeps a closing between episodes inside its part; `--part-labels=A,B,…` names the parts (marked `source.label: "editor"`, which the Book view's contents show in parentheses and lighter; an empty name leaves a part untitled, as the contents then say). Episodes are named and numbered from their closing lines, and each part records how its start and end were found. Run it on a baseline. For the Rāmāyaṇa-mañjarī (method 100) it makes seven parts as the book closes them (the Bāla and Ayodhyā together, as printed, and an untitled part between the Yuddha and the Uttara), with 202 episodes.
- `tools/chaya_verse_groups.mjs IN OUT [--counts=NAME=N,…]` groups verses that make one sentence, printed with a marker after them ((युगलकम्) two, (तिलकम्) three, and so on): each marker and the verses printed just above it on its page (reading order is not trusted) become one `verse_group` unit, the marker last; a marker read as the last line of a verse is split off first. The reader floats the marker after the group's last line, so it takes the free space at the right of that line where it fits (and the space under it where it does not) without interrupting the spacing of the verses, and lights the group when the marker is hovered (or tapped in the Book view). Run it after `chaya_baseline.mjs` and before `chaya_sections.mjs`.
- `tools/chaya_page_labels.mjs IN OUT [--report=FILE]` reads each page's label again from its page-number text (as the app does after reading; a re-reading by a tool may leave the old label), then corrects the labels by their sequence, every page counting: between two runs of at least three pages that agree and imply the same numbering, the pages take the numbers implied (the page-number text with them). A change of numbering (front matter, then the body) is listed, not changed.
- `tools/chaya_html.mjs IN.chaya.pdf OUT.html` writes the book as one standalone web page, laid out as the Book view (pages with transcription, dimmed pages left out; figures empty).
- `tools/chaya_rescale.mjs IN OUT [--dpi=300]` redraws a book's pages at another size: each page's width and height become its size in points at the dpi, and every outline and box in its documents is scaled; `image_sha256` is dropped and the saved model records are left as made. For a book made before `scanImage` took the sharpest image on a page (an archive.org scan's background instead of its text layer).
- `tools/chaya_verse_numbers.mjs IN OUT [--type=verse] [--report=FILE]` checks the numbers printed at the end of verses ("॥ १२८ ॥") against their sequence and corrects stretches misread by one digit (by at least 2, so a skipped verse is not taken for a misreading), and a first number after a restart read ९ for १; restarts and other breaks are listed. `--type=section_closing` does the same for episode numbers on closing lines. Run it before `chaya_sections.mjs`, which names and numbers each episode from its closing line.
- `tools/chaya_rules.mjs IN OUT [--closing=TYPE] [--part-closing=PATTERN] [--part-heading=PATTERN] [--part-after=PATTERN] [--division-closing=PATTERN] [--part-labels=A,B,…] [--marker-type=TYPE] [--counts=WORD=N,…] [--clear]` sets a book's structure rules in `book.json` and writes a copy. The Rāmāyaṇa-mañjarī's are those of `methods/100-hydrogen-low-whole-page-reading/pipeline.sh` (`--part-closing='कथासारे' --part-heading='काण्ड' --division-closing='किष्किन्धापर्व'` and its seven part names).
- `tools/chaya_notes.mjs IN OUT [--report=FILE.json]` links footnote markers to their notes by rule (`js/note-links.js`), with no model. A marker the transcription left as text (a superscript span, ¹, `<su>१</su>`, "(१)" or digits against a letter) becomes a note marker. With `--from-quotes`, a note that quotes a reading and has no marker gets one after the word clearly closest to the quote, kept only while the placed markers follow the notes' order; that is off by default, because a note's quote does not always name its marker's word (method 099, page 60). Each marker is then linked to the note on its page with the same number. Read → Problems lists, page by page, the notes with no marker and the markers with no note. On the finished Rāmāyaṇa-mañjarī, 616 of 711 notes link to their markers. The Hydrogen reading supplied the markers.
- **The books so far** are in `outputs/books/`, as folders and as `.chaya.pdf` files:

## Tests

```sh
node --test $(ls webapp/test/*.test.mjs | grep -v page-joins)  # from the repository root
node --test webapp/test/page-joins.test.mjs                   # run separately
UV_NO_SYNC=1 uv run --offline python schema/test_book.py
node webapp/test/browser.mjs SCRIPT.mjs            # drives headless Chrome through a script (see the file)
```

- `parity.test.mjs` runs the app's checks and assembly against `book.py` and `inline.py`: every page of the two books (447), 233 broken copies of 23 of their pages (12 kinds of fault, such as an unknown type, a duplicate unit, an open end on a middle child, a span outside its text or an unknown anchor), the two assembled books, and inline parsing cases.
- `ops.test.mjs` runs every kind of edit on real pages, checks the results, and undoes them.
- `fragment-lines.test.mjs` checks detached glyph parts, separate short lines, stable line IDs, text and span preservation, repeatable updates, and relations addressed by line. The current settings match method 094.
- `flatten.test.mjs` checks that the flattening equals the Python result on a shared fixture, leaves white paper unchanged, moves near-white paper by at most one level, and keeps the line ends that touch a dark band along the page edge (which method 093 loses).
- `paper-threshold.test.mjs` checks that a grey-paper page fails with the old weak threshold and gives its lines with the paper-relative one, that a white-paper page is identical under both, and that the paper level matches its numpy definition.
- `local.test.mjs` runs the port with the legacy settings on six pages against method 043. The threshold, component count, character height, page angle and line centers are identical; every region gets the same line pieces; and the outlines' pixel overlap is 0.98–1.0 per region. It also checks that recomputed outlines keep every line's text.
- `pipeline.test.mjs` checks the region and transcription prompts and schemas against methods 042 and 055 for every type list (byte for byte), and the copied templates and type lists.
- `pagedoc.test.mjs` builds the page documents of method 055's six test pages from their saved answers and region records, and compares them with method 055's. Two additions are left out of the comparison: each region's `box`, and a relation without a marker sign anchored to its line's only marker.
- `readers.test.mjs` covers reader options, costs, reading contracts, authoritative reader text, OCR word mapping, checked-reference scoring, cache reuse and invalidation, failed paid calls, concurrency, neighbor context and URL-book export persistence. Integration cases check request and fingerprint parity, geometry-key migration, corrected page inputs, drafts, protected edits and read-only run isolation.
- `recipe.test.mjs` checks the default recipe against the model lists and defaults, the stage lines, and estimates from a book's own calls, from the measured figures and for unmeasured or local models.
- `disk-copy.test.mjs` checks the copy on disk with a simulated clock and file: writes at most every five minutes, checkpoints, changes during a write, lost permission and its request, failed writes, a damaged book never replacing the copy, the spending check and the header labels. It also checks that opening names lost source PDFs and page documents, restoring from a `.chaya.pdf` of the same book, and change reporting.
- `store.test.mjs` checks style saving, journal recovery at every stage-save file boundary, failed writes and retries, newer drafts, cross-instance edits and concurrent manifest updates.
- `stages.test.mjs` validates provisional documents on the nine public region references and checks stage states, legacy blank/illustrated pages, protected edits, geometry and text compatibility, marker parsing, invalid candidates and note-link matching. The pipeline uses these foundations. The five-tab interface and page grid are step 3 of HANDOFF.md.
- `workflow.test.mjs` covers stage readiness and routes, reading gaps, review-mark persistence through a book PDF round trip, batch stopping, credential errors and stale checks.
- `type-tree.test.mjs` checks the containment tree of By type (each type once under its first container, nested containers, cycles, notes and counts).
- `find-targets.test.mjs` checks which pages Find regions uses in By page and By type, and that the credentials box asks for one key per provider.
- `reading.test.mjs` checks the one reading path: for the public fixtures and, where present, both finished books, the assembled book through `toBlocks`/`fromBlocks` (units, flows, relations, warnings) equals the saved one; a 0.4 page is used as it is; the reading is kept while pages, rules and dimmed pages are the same; the rules' defaults, partial settings and invalid patterns. `blocks-schema.test.mjs` checks that 0.4 pages pass `checkPage` and `schema.json` and that bad overrides are found.
- `empty-page.test.mjs` checks a page with no content (all its regions removed, as "No content on this page" does): it passes the checks, has no review flags and needs no paid transcription or completion, Read shows nothing of it and joins the paragraph across it, and Problems and the flags find nothing there.
- `join-partner.test.mjs` checks finding the page that continues a unit for a hand-join, past blank pages and plates, and where the search stops.
- `skipped.test.mjs` checks dimming pages: saved in `book.json` in page order, announced as a change for the copy on disk, removed when none is dimmed, never changing the page list, and refused for a read-only book.
- `page-joins.test.mjs` checks joins across pages with no unit of the type, flat and inside chapters: a blank page, a plate with and without its caption and furniture, a paragraph on three pages, a page with its own paragraph that stops the join, a verse past a page of prose and a paragraph and a verse that do not join, open starts with nothing to join, a region continued on its own page (not a page-break continuation), gaps in Read, the Read flags and the Regions continuation flags with their limits; and that `book.py` assembles every case the same way.
- `finders.test.mjs` checks block grouping, coarse type guesses, saved choices, reviewed layouts and frozen provider requests.
- `credential-cache.test.mjs` checks that a successful key check is remembered across reloads as a digest (never the key), applies only to the same key and model, and is removed by a failed check.
- `finder-proposals.test.mjs` checks method 097: the request lists pending proposals, proposed-type regions become unassigned regions with `proposed_type`, names merge ignoring case and separators, a run's later pages see earlier proposals, recorded proposals assign waiting regions on unprotected pages and only list protected ones, and persistence through the work files and a `.chaya.pdf` round trip.
- `proposed-type-check.test.mjs` checks the page editor's “Add type X” check item (with Review area and Leave out), and “Use type X” when the name is already listed.
- `review.test.mjs` checks human choices, marker links, stale scores and snapshots, subtree scope, replacement stages, and interrupted review saves.
- `read-regions.test.mjs` checks region edits in Read on a page whose units are settled (a section open at the page's end, a paragraph of two regions, a linked note): retyping in place, out of a section into another flow, out of a unit of several regions, to and from furniture; drawing where drawn, into a chosen unit and into the innermost of nested sections open at both ends; deleting down to an empty flow; splitting with its links; merging; Earlier and Later with open ends; each leaving the page valid with its text, and a provisional page rebuilt.
- `editing.test.mjs` checks focus locks, provisional reading, logical-unit fragments, semantic metadata, stage-preserving saves, stale snapshots, cross-page joins, recovery after interrupted two-page writes and coherent export.
- `browser.mjs` is a small headless-Chrome driver over the DevTools protocol (no packages), for scripted runs of the app itself.

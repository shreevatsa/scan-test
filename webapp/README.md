# The web app: reading and correcting digitized books

A static web app for the books this repository's methods produce. It runs entirely in the browser with plain HTML, CSS and JavaScript modules, bundled PDF and OCR runtimes, and no build step. A book consists of its PDF and page documents (schema 0.2 and 0.3, [schema/README.md](../schema/README.md)), kept in the browser and saved together as a **.chaya.pdf** ("Books" below).

Agents preparing a book can use [the portable transcription skill](../skills/transcribe-chaya-book/SKILL.md). Its folder contains a general workflow, a self-contained format reference and a Python PDF packer that work independently with public PDF tools and the chosen OCR engines or models.

The five workflow tabs are **Pages · Regions · Text · Read · Export**.

- **Pages** browses the scans and shows all three layers of progress, with filters for layer states and flags. Open a thumbnail for a scan preview, with previous and next, before processing anything. Nothing in Pages acts on a selection, so its grid has no selection controls.
- **Regions** has **By page** and **By type** views for the evolving schema and its assignments. Find or draw regions, review their types and reading order, then move pages on to Text together.
- **Text** lists pages with accepted regions, compares and runs transcription models, and moves reviewed transcriptions on to Read.
- **Read** shows accepted text. Its Units and links view runs completion separately. Completion comparisons, Problems and Style sheet are also here. Pages not moved on to Read yet are marked, and units do not join across those gaps. Units do join across a blank page or a plate (Read, below).
- **Export** keeps the book's copy on disk and saves the book PDF and source PDF at every stage. Text-based exports become available after some transcription exists.

Text and Read are disabled until pages are moved on from the preceding stage. Legacy documents infer acceptance. A book with pending pages opens at Pages, while a complete legacy book opens at Read. Old bookmarks route to their corresponding views. Each stage grid opens the page editor with previous/next eligible page, a next-flagged-page button and links to the same page in other stages. Regions, Text and Read each open the editor with controls for that stage.

Each stage grid (Regions → By page, Text, and Read → Units and links) has the page grid under its heading. Its model, credentials, spend threshold and run controls are in one **Process pages** section. The section's summary is the stage's one line, such as "Regions with GPT-6.1 Terra · reasoning off · about $0.01 a page", with the pages still to process. Inside, that line has **Change**, which opens the model list and the comparison for that stage: the inline finder comparison in Regions, "Compare transcription models" in Text and "Compare completion models" in Read. The comparison views are reached only from there, and their header tab shows only while one is open. It starts open only while pages wait for that stage's processing, and remembers being opened or closed while the book is open. The pages a run applies to are chosen in that section, above the run button, by typing a range such as `1-50, 62` into **Select pages** and pressing Enter (or by ticking pages in the grid, which fills the box; clearing the box clears the selection). "Move on" and "Send back" sit in a bar at the bottom of the screen, which says which pages they apply to. The credential panel has its own box and closes once a key checks. The two redo options are under "Redo options": skip pages that already have a result unless "Also redo" is ticked, and reuse saved model results unless "Ignore saved model results" is ticked. A read-only book (opened where the browser keeps no books) has none of these: one line offers "Make an editable copy" instead. It also has no "Review page with AI", type proposals or comparison tabs.

The stage grids support checkbox selection, shift-click ranges and the Select pages box (`all`, `1-50,62`). With no selection, actions target the displayed pages that are not dimmed (below). A typed range leaves out dimmed pages too; ticking a dimmed page in the grid includes it. Filters cover layer states, flags, rare layouts (Regions), earlier type revisions and suggestions. Explicit selections hidden by a filter are counted in the selection summary. Moving on and sending back are saved in the document and survive a book PDF round trip.

**Dimming pages.** On Pages, a small × on each page's preview marks it not interesting: it is shown faded in every grid (↺ brings it back), and runs and moves that default to the displayed pages skip it. This is only a default: the page stays in the book, in the counts, Read and the exports, and ticking it in a stage grid includes it (a typed range does not). The Pages summary counts the dimmed pages and the page filter has "Dimmed". The list is saved in `book.json` as `skipped` (page ids, in page order), so it survives a reload and a `.chaya.pdf`, and writing it makes the copy on disk be written again. A read-only book cannot dim pages. A page that should not be in the text at all is given no content (below).

**A page with no content.** A new book has every page of its PDF. A page that is not part of the book (a library's cover, a blank page, another work bound in) is kept with no regions. In the Regions editor, **No content on this page** removes every region of the page as one editing step, with the page's printed lines outside the regions, its unassigned regions and the region finder's notes, and moves the page on to Text. It asks first when a region has text or the page has the person's edits, and undo brings the regions back while the page is open (the page is then back in Regions, its regions saved as an edit). A page with no regions has the layout "Blank page". It has nothing to transcribe or complete, so Text and Read count it as done (its badge says "No content"), and their runs and cost estimates leave it out; moving it on from Text gives it an empty text layer, with no model call. Read shows nothing of it, and a paragraph that goes on across it is one unit, as across any page with no unit of its type (Read, below).

In Regions → **By page**, **Process pages** holds the finder's line (Change opens the finder list, Draw by hand, the OCR language pack and the inline finder comparison), credentials and the run controls. The page grid has colored region boxes and can be grouped by layout, rarest first. A page's layout is the kinds of content on it (its non-furniture region types, in the type list's order), not how many regions there are or their order, so ordinary pages fall into a few groups. The editor’s **On this page** legend shows the types present and their region counts. Clicking a type opens its examples in By type. **All book types** expands the complete list. Hovering a region shows its type and highlights its card, and hovering a card highlights the scan. A blank-page click clears the selection. Pending-transcription regions use compact cards. **Edit type list** opens the full list in a dialog and retains the current page and selected region after a revision. “Start by hand” creates an empty provisional page. Draw boxes, choose their types, set reading order and continuation flags, split at a line piece or merge same-type regions, then move the page on to Text. **No content on this page** is for a page that is not part of the book (above). Existing transcription is shown read only. Keys 1–9 assign the corresponding printed type to the selected region, and Tab or Shift+Tab selects the next or previous region while working on the scan. On phones, the scan and controls stack vertically.

Regions → **By type** shows each definition, containment rules, measured page coverage and six scan examples at a time. Examples from different pages appear first. Printed types show their region crops and outlines. Containers show their descendant regions on the page, with provisional grouping labelled. Opening an example selects its region in the page editor. The editor also shows the selected type’s definition and offers **Examples of this type** and **Edit type…**. Switching views retains the selected type, example batch, page, region, zoom and pane scroll positions within the open book. Grid selection, filters and scroll position are retained too. The complete tree, table, review questions and revision history remain under **Full schema and revision history**. Old `#types` and proposal links open the corresponding Regions view.

Unassigned model regions are hatched and have “Give it a type” controls. Review flags include uncertain or unknown types, missing order, empty regions, uncovered printed lines, overlapping regions, provisional containment problems and continuation disagreements. Two regions overlap when more than a fifth of the smaller is covered: by their outlines where both have them, so a two-line footnote beside one-line footnotes is not flagged. Continuation flags are compared across a page break only while either page's units are provisional; settled units are checked by Read's assembly. They follow assembly's rule (Read, below): a page's first region marked as continued from the previous page, or its last marked as continuing, is compared with the nearest page past pages with no region of that type in the flow and no such mark (a blank page, a plate), and a page between is not flagged. They look no further than a gap in the PDF's page numbers, a break between sample pages or a page with no document yet. A rare layout is a filter and a grouping, not a flag. Text and completion flags are computed separately for their stages. Pages shows each page's flags at the stage it waits at (the first layer not moved on, else Read). `node webapp/tools/flag_counts.mjs BOOK.chaya.pdf` counts the flagged pages per stage and flag kind.

“＋ Type” adds printed types and containers. A container starts with at least one child type. “New type…” in a region menu adds a printed type for immediate assignment. By type has forms for descriptions, renaming, merging, splitting, containment, flow, printed class and unused-type removal. “Edit book details” changes the title, description, languages and transcription conventions. Each operation previews its reach across model pages, saved corrections and drafts, with affected PDF pages, follow-up work and estimated model cost.

Renames update region and unit types, containment rules and the style sheet, with old names recorded as aliases. Merges require the same printed class and furniture role, or two containers. An existing target style takes precedence. Transcription is preserved. Containment changes rebuild provisional or unprotected units where needed and flag protected units for manual repair. Figure-class changes retain text in provenance and flag region discovery. Unused-type removal checks every document version and draft.

**Regions → By type → Propose and compare unit types** offers a whole-book overview or selected pages in detail and saves attempts inside the book. A reviewed proposal can replace the list while every page’s layers are unprotected. The preview identifies the documents to clear and the region work to repeat. Previous types and page versions are retained in revision history. Review questions link to cited sample pages and retain recorded decisions. Revisions, aliases and historical prose notes are saved with the book. Multi-file operations use a recovery journal and a book write lock, including draft migration and coherent book exports. Work records retain their original bytes, with aliases applied when reading copies.

- **Page editing** shows the scan and line outlines beside the transcription.
  - Regions edits boxes, region types, reading order and continuation flags. Its transcription is read only.
  - Text edits line text, inline formatting, printed note markers and the printed page label. Boxes, unit grouping and line joins are locked. “Review re-transcription of this page” selects the page in the Text overview with reprocessing enabled.
  - Read edits unit types, numbers, labels, grouping, open ends, note links and line joins. Transcription and page geometry are locked. A unit can be split between children, joined to the next unit, wrapped, unwrapped or converted to page furniture. Unit and line presentation styles remain available in this fallback editor.
  - Hovering a line highlights its outline. Zoom, fit width and fit height work in every focus. Fit height is retained across pages and resizes.
  - Text inserts note markers at the caret and changes their printed signs. Read assigns their note links. Line joins have explicit controls and can also be cycled at a line’s right edge in Read.
  - Changes are checked and autosaved. Invalid edits are retained as drafts. Undo and redo cover page edits. “Revert page” returns to the latest stage save.
  - Focused saves preserve newer work in other layers. Concurrent changes to the same text or unit grouping require a fresh selection or reload.
- **Read:** the whole book as one text, assembled from its pages as `book.py assemble` does, with the user's corrections.
  - A unit open at the end of a page joins the unit of the same type open at the start of a later page of its flow when every page between has no unit of that type there and no open end of its own: a blank page, a plate (a figure, with its caption and running header), a page of other kinds of units. Their units follow the joined one, so a plate's figure comes after the paragraph it interrupts. A page between with a unit of that type, or with an open end of its own, stops the join, and the page break is a problem. The same rule holds a level down (a paragraph inside a chapter that goes on across a plate). Pages not moved on to Read are gaps that nothing joins across; Problems and Export, which assemble every page with a document, treat a page with no document yet the same way.
  - Headings, verses, paragraphs, tables and notes are shown according to their types, with formatting. Figures are shown as their part of the page image, with their label.
  - Note markers link to their notes and back.
  - The printed page number is shown where each page starts.
  - Clicking a passage opens its scan and clickable unit ancestry in a side panel. Editable books expose unit fields, grouping, line joins and note links there. Double-clicking opens the page fallback.
  - A cross-page unit has page-fragment navigation. Its semantic fields and wrapping apply across all fragments. Splits and open ends apply to the selected fragment. Joining at a page break opens the matching ancestor paths on both pages. The unit continues on the next page, or on the first later page that has a unit of its kind, looking past pages with none and no open end of their own (a blank page, a plate), as assembly does; it stops at a gap in the PDF's page numbers, a break between sample pages or a page with no document yet. Conflicting metadata requires review.
  - Each saved change reassembles the reading and retains its scroll position. Problems appear beside their passages and in a list. Read-only books expose inspection controls.
  - Text can be read before completion, with provisional grouping identified and line ends treated as spaces until completion. The side panel stacks below the text on narrow screens.
  - "Show the units" shows the unit tree in the margin.
  - Units in a row stand side by side where the width allows, and one under the other where it is narrow.
  - "As printed" (for a book with a style sheet) sets each unit as the book prints it: fonts, sizes, alignment, margins, indents and spacing, from the style sheet and the units' own styles, at the book's measure.
- **Regions → By type** shows the book's type list, its own part of the schema (the format, `schema/schema.json`, is shared by every book).
  - the tree of what may contain what, from each flow's top level, with how many units of each type stand in each place;
  - the page furniture types;
  - a table of each type: its region class, what it may contain, its flow, language, numbering, total and description;
  - the relations, inline kinds and transcription conventions.

  Operation forms preview and apply changes. “Download types.json” gives the file, and the revision history records applied operations.
- **Read, Style sheet** the book's style sheet (schema 0.3), seen and edited:
  - the base style of all text and each type's style (font role, size, leading, weight, italic, alignment, left margin, first-line indent, space above and below), in a table where an empty cell inherits the base;
  - the font roles and their font families;
  - the page's size and text box (whose width is the measure).

  A preview of a few pages, set as printed, follows every change, and each change is checked against the schema. "Save" writes `style.json` into a book folder (and names it in `book.json`). For a read-only book, the sheet is kept in this browser over the served one, until "Back to the book's own". "Download style.json" gives the file. A book with no style sheet can start one from plain defaults. Units' and line pieces' own styles are set in the page view.
- **Read, Problems** what the checks find across the book (as method 047's `book_report.py`):
  - pages whose document fails the checks (the schema and the type list's rules, as `book.py check`), whose corrections are kept as drafts until they pass;
  - page breaks where units marked as going on do not join;
  - printed page numbers out of sequence. Pages that print no number, as a chapter's first page, are listed apart, as a note;
  - which pages the user corrected, and the transcription model's notes.
- **Export:** the book as one document of the book schema (JSON), the book as plain text with page references (a figure as `[figure: label]`), the book as one web page (HTML, as printed where the book has a style sheet, with its figures embedded), and the user's corrections as one file (and importing such a file).
- **Stage processing** makes page documents in the browser with the user's API credentials. Regions finds and types regions with its selected finder, Text runs the selected transcription model, and Read completes units and links with its selected model.
  - **The recipe** (`js/recipe.js`): a new book starts with GPT-6.1 Terra regions (methods 042 and 063), Gemini 4 Argon low transcription and Gemini 4 Argon high completion, saved in its `book.json`. A type proposal's or an excerpt's model choices replace it. "Change" in a stage chooses another model for the book.
  - **Cost before a run:** each stage estimates new work from the book's own completed calls of that model (their mean cost a page). Until it has some, the recipe's models use the cost measured on a 267-page scanned book: about $0.010 a page for regions, $0.038 for transcription and $0.032 for completion. Another model without the book's own calls says it has no measured cost yet. Local models are free. The estimate after moving pages on to Read uses the same figures. The comparison views offer an editable copy of a URL book. For an excerpt with a larger cost-projection target, “Start from the full PDF with these settings” opens a new-book form carrying the current types and model choices.
  - **Making a book.** Open a plain PDF from the library to create a book from the whole PDF: every page is in it, and a page that is not part of the book is given no regions in Regions ("A page with no content", above). The form defaults to common draft types, which can be refined in Regions, and the book starts with the recipe (above). Alternatively, propose book-specific types from sample pages or supply an existing list. Browse all PDF pages as thumbnails, open larger previews and check pages to include. The sample field accepts `all`, ranges such as `1-50`, and lists such as `1, 7, 43-44`. Request a proposal from GPT-6.1 Terra with reasoning off or Gemini 4 Argon with high thinking after checking the credential. The review shows descriptions, containment rules, reading flows, links, inline kinds, transcription conventions, supporting page references and questions. Descriptions and grouping rules can be edited before approval. A model proposal must be reviewed before use. Continuing from an excerpt carries over that book's types and model choices.
  - **Unit-type proposals** use rendered page images and the user's description. The default sample spans the beginning, middle and end, including two neighboring middle pages. The sample is editable to include contents, section openings, ordinary text and special layouts. Each explicit proposal is one model call whose estimated charge is shown with the result. API keys are configured in this browser. Attempts and the latest saved proposal are retained by PDF hash before a book exists. Creating the book includes these records in its work files for export. The recipes are [method 077](../methods/077-gpt-6-1-terra-unit-types/README.md) and [method 078](../methods/078-gemini-4-argon-high-unit-types/README.md).
  - **The source PDF:** the PDF is copied into the folder as `source.pdf`, the book's source.
  - **Page images:** each page is analyzed (its images, where they are drawn and how much of the page they cover, and its text layer's characters) and rendered with the bundled pdf.js. A scanned page (an image covering at least half of it) is rendered at 300 dpi, or at the scan's own resolution when that is lower; any other page at 300 dpi. The cap no longer applies to a digital page with a small ornament, which it used to lower to 240 dpi.
  - **What each page records:** its PDF page, its rendering, its images and its text layer's size.
  - **Regions** use the selected finder and the local step of methods 063 and 093 in the worker (093 sets the weak ink threshold from the page's paper level, so grey paper no longer fails as too little text). Models use method 042's book-specific prompt and schema. Free finders supply coarse blocks for manual review. Per-finder results are saved under `work/region-finders/<page>/<profile>.json`. Normal stage processing also writes the active `work/<page>.regions.json` and merges an editable provisional page document.
  - **Transcription** uses the per-book choice of Argon low or high, Flash low, Flash-Lite minimal, local Tesseract, or Cloud Vision Text Detection or Document Text Detection. The language models receive the overview and numbered region cut-outs. Tesseract and Cloud Vision map full-page word boxes to shared source-line polygons.
  - **Schema assignment** uses text-only input with Argon high or low, Flash low, Flash-Lite minimal, or Terra with reasoning off. It builds unit trees, joins, continuations and note links while the app retains the selected transcription model’s text. Argon high is the default for existing books. Transcription and schema assignment are saved independently for each model. Batches transcribe all queued pages before schema assignment, so adjacent readings are available.
  - **Retries and caching** reuse matching successful stages. Transcriptions also match by image, model and region/line polygons, so changing types, conventions or reading order reuses the reading. Older reading records gain this geometry key when used. Completion takes current corrected text, formatting and note markers, retaining the old completion fingerprint when their content is equivalent. A failed structural call can be retried without repeating transcription. The Transcription models tab also offers an explicit new structural call for a selected result.
  - **Changed-region transcription** compares the current shapes with the same model's saved reading. Only changed or added text regions need new model output. The result combines them with compatible saved regions. After a box edit, open Text, include the processed page and click “Transcribe”. Leave “Request fresh model results” unchecked to use repairs. “Review re-transcription of this page” prepares that selection from the editor. An explicit fresh request processes the whole page. A full pass is also needed when there is no compatible saved text for the scan, chosen model and OCR language.
  - **OCR repairs** reuse Cloud Vision's saved full-page word boxes when available, with no new Vision charge. Tesseract runs locally on the full page to keep word assignment consistent, then merges only the changed regions. Completion uses the full current transcription, including human corrections.
  - **Repair recovery** archives the prior reading and retains each contributing call. Completed partial responses can be reused after an interrupted save. An unresolved partial attempt requires review before an explicit fresh whole-page request. A newer cached reading is preserved when an older call finishes later.
  - **Saving stages** merges the latest page and preserves edited or accepted layers. Conflicting candidates are recorded in `source.suggestions` with their work-record paths. A valid draft participates as edited content. An invalid draft stops the model step. A journal in `work/pending-stage/` makes the model document, manifest and removal of the merged edit recoverable together. The previous protected page is retained in `work/history/`. Opening or exporting a book recovers pending saves. Comparisons and read-only books keep their trials in work records. Suggestions open in the shared review dialog.
  - The keys are kept in the browser (IndexedDB) and sent only to OpenAI and Google. Costs are estimated from returned usage, including thinking, cached input and OpenAI cache writes, at the recorded paid-tier prices. Unavailable costs are displayed explicitly and stop further calls in the batch.
  - **Processing a book** starts in Regions. Select pages, check the credential and find regions. Move reviewed regions on to Text, transcribe there and move reviewed text on to Read. Complete units and links in Read’s grid. Each stage has a spend threshold, progress and a stop button. Ordinary provider requests have a 75-second deadline. Whole-book contact-sheet discovery has a five-minute deadline. Existing layers are skipped unless included explicitly. A separate checkbox requests fresh model results. Compatible cached trials are reused. A paid run first checks that a copy outside the browser has the latest change ("Before spending", under Books). Review Problems, correct individual pages and keep the `.chaya.pdf` on disk from Export.

Book cost projections recover original whole-page prices from reading history after region repairs. Each stage uses its available measured samples. A missing stage is named beside the dollar subtotal until a full total can be estimated. The saved API-attempt ledger includes repair and retry charges. Composite readings deduplicate contributions from a reused OCR response by its call path.

## Reviewing one page with an AI instruction

Open a page in Regions and click **Review page with AI**. Choose Terra with reasoning off or Argon with high thinking, enter an instruction, check the credential and click **Review this page**. The model receives the scan, its current region assignments, the book’s type list and the instruction. Each explicit request is a billable call with saved usage and estimated cost.

The result contains an explanation, optional printed type additions and a complete proposed region layout. **Review type additions** opens the ordinary revision preview. After the proposed types are available, **Review proposed regions** computes local outlines and opens the shared layout comparison. Applying its reviewed choice updates the page. Adding a more specific type supports retyping this page while the full type editor remains available for wider revisions.

Responses are saved with the book and restored on reopening the form. Raw calls retain the instruction, input type list, scan hash and dimensions. The call ledger can recover a response if its latest pointer failed to save. Region previews check the scan and proposed definitions before applying the normal review logic. The recipes are methods 087 and 088.

## Reviewing suggestions and model differences

A saved result held back by protected work appears as a suggestion in its stage grid, page editor and reading panel. Open it to compare current and proposed versions against the scan. Keep the current version, take the proposed version or dismiss the suggestion. Saving a choice protects the reviewed layer. A partial choice retains the suggestion for the remaining items.

For a repair using the same model as the page, the suggestion keeps current transcription in unchanged regions, including human corrections and printed-marker identities. Those regions are labelled “Current text retained”. Model comparisons continue to show the model's saved text.

The same dialog is available from transcription and completion comparisons. Choose a whole page, one region or one text line, and correct the chosen line when needed. A grouping choice replaces the smallest complete shared subtree. Changes to ancestry, flow or linked units may require the whole page. The preview reports the number of regions affected, transcriptions becoming pending and removed links. Invalid or stale choices require a fresh review.

Reviewed text supplies checked-error scores. Completion scores use reviewed structural fields whose input and current page choices still match. Counts of model differences remain separate. Review saves and their evidence share a recovery journal, with the previous page retained in work history. Saving choices requires an editable copy of the book.

Whole-book type discovery renders all PDF pages into labelled contact sheets, with previews and larger evidence-page views. It uses Terra reasoning off or Argon low through methods 091–092. A request contains at most 16 sheets and 12 MB of serialized payload. Larger books split into saved batches. Overview counts are estimates computed from a validated page inventory. The type list also shows page counts measured from saved regions and units, and those counts open the affected pages in Regions. A five-minute deadline applies to overview calls. Completed batches are reused, raw completed calls can recover failed batch-pointer saves, and unresolved attempts require an explicit retry. The previous selection is retained in work/type-discovery/history/.

Type discovery can run both existing proposal models and build one draft. It identifies shared names and model-specific types, shows definition differences, and lets the reviewer keep, drop or choose a source definition. Approval and application use the same type-list preview as single-model proposals.

## Choosing and comparing region finders

Open **Regions → Process pages → Change → Compare finders**. Use the page grid selection or enter sample positions with `all`, ranges or lists. Compare Terra, Astra low, GPT-6.1 Sol low, the four Gemini variants, local line blocks and Tesseract paragraphs. The reference finder is included in each run. Select a free reference and free candidates to compare with zero API cost. Credential checks are grouped by provider and verify access to the selected models. Progress, stopping, a spend threshold and cache reuse work as in the other comparisons.

Every saved candidate has a scan overlay, its region types and reading order. Amber blocks need a type. A page already prepared in Regions can be reviewed against a candidate in the shared dialog. Replacing its layout is a whole-page decision, with a preview of affected transcription. Exact matches to explicit human choices are counted separately from differences against a model reference. Click **Use this finder** on a result to save the choice, then process selected pages in Page regions. Existing work remains protected through suggestions.

Free blocks are intended for manual correction. They guess only coarse classes and map a class to a book type only when exactly one matching type exists. All local guesses are marked uncertain. Tesseract uses automatic segmentation mode 3 for layout and the selected OCR language pack. Its transcription path uses mode 6. The region choice and shared OCR language pack are saved per book. The single whole-book cost estimate includes region finding plus the selected transcription and completion sample costs. It assumes downstream costs stay at their sampled level and requires all three stage samples.

Methods 079–086 retain the nine-page public benchmark and frozen runtime. The 54 model calls cost an estimated $1.700885. Astra, Sol and Argon high matched every reference passage boundary and grouping in this run. Semantic type and continuation accuracy require separate review. Lower Gemini settings and both free finders had substantial grouping errors on several pages. See NOTEBOOK.md for the full table.

## Choosing and comparing transcription models

Open **Text → Process pages → Change → Compare transcription models** (`#text&view=compare`) in an editable book; a read-only book shows its Text grid with "Make an editable copy" instead. The selected transcription model, schema assignment model and OCR language pack are saved per book. Trial page selections, reference, inspection choices and estimate page count survive reload. Argon low is the default transcription model for existing books. Page-region detection uses the finder selected under Regions. The page runs from sample comparison to source review, then ends with “Choose the transcription model for this book”. Select a model and press “Use transcription model for this book” to save that choice, then continue to the schema comparison. Whole-book estimates hold the selected schema assignment model fixed across transcriptions. Its optional execution checkbox is under “Whole-book estimate settings”.

Choose sample pages, candidate transcription models, a reference transcription and a spend threshold. Check each selected service under API keys before running. Gemini and Cloud Vision have separate checks. Selecting additional models or changing a credential updates readiness. Schema comparisons use the same checks, and local OCR needs no key. The reference source can be a model’s saved transcription or the current page text. Argon high is the default reference. Carbon high is opt-in. Schema assignment is included by default. A progress bar counts processed steps across shared region checks, transcriptions and optional schema assignments. The display includes elapsed time, reused results, failures and skipped steps. Stopping or reaching the spend threshold keeps the actual processed count and percentage. The table shows one whole-book cost estimate, transcription-plus-schema elapsed time and schema checks. Set the target book’s page count, or enter 1,000 for a normalized comparison. It defaults to the manifest’s optional `cost_projection.page_count`, then the source PDF’s page count, then the listed pages. An optional `cost_projection.label` names the default target for an excerpt. The estimate averages the available sample costs of each stage, then multiplies by the target page count. The fixed schema model’s measured price is shared across transcription candidates. Original whole-page readings remain price samples after region edits, with their use identified in the table. Shared region detection counts once per page in every model’s projected pipeline. A stage with no measured cost appears by name beside the subtotal. Projections cover one pass at the sample calls’ recorded prices, with schema validity shown separately. Failed attempts and unresolved charges appear in the ledger. The threshold is checked between calls and can be exceeded by the final call.

Inspect the transcriptions lists saved comparable pages across the book in source order, with 20 regions per batch and a PDF page heading for each group. The default filter shows differing regions. Turn it off to include agreeing regions. Batch navigation retains its position across reload. Regions and whole-page review actions target the displayed source page.

## Running it

Serve the repository root and open the app, for example:

```sh
uv run --offline python -m http.server 8765 --bind 127.0.0.1      # from the repository root
open "http://127.0.0.1:8765/webapp/"
```

Then, in the library:
- **Open a PDF or a .chaya.pdf…** A plain PDF starts a new book, or opens the book this browser already has from it. A `.chaya.pdf` goes into this browser, or offers to replace the browser's copy, open it, or keep both.
- **Books in this browser:** open one, download its `.chaya.pdf`, or delete it. Each row says when its copy on disk was written, or that it has none. Below the list the browser's answer on persistent storage and the space used are shown. A folder in the browser's storage without a readable `book.json` is listed with "restore…" and "delete…".
- **Open a PDF by URL** (`?book=<url>`): the app fetches the PDF and opens it exactly as a PDF chosen from disk (a `.chaya.pdf` is imported as a book in this browser, with the same prompt when the browser already has it; a plain PDF starts a new book). The server must allow the fetch (same origin, or CORS), such as `http://127.0.0.1:8765/webapp/?book=../outputs/books/kale-1913.chaya.pdf`. Where the page is not served over https or from localhost, a `.chaya.pdf` opens read only instead, with corrections kept in IndexedDB.
- A plain PDF can also supply `&proposal=<url>` to preload a saved unit-type proposal. Its source PDF hash, type rules, page evidence and call metadata are checked before review. Reviewing this saved result and creating the book require no API key. The user must approve the types. Saved call records and optional transcription/schema model choices are copied into the created book. The proposal review's **Saved proposal JSON** section provides the transferable package. Locally edited proposals take priority when reopening the same PDF.

Keeping books in the browser, and the hashing that checks a `.chaya.pdf`'s original, need a secure context: `https`, or `localhost`. Served over plain `http` to another name (such as a Tailscale address), the app opens a `.chaya.pdf` read only, and says so in the library.

For access from a phone or another device on your tailnet, run `tailscale serve --bg http://127.0.0.1:8765` and open `https://<machine>.<tailnet>.ts.net/webapp/` with Tailscale connected. On macOS the CLI may be `/Applications/Tailscale.app/Contents/MacOS/Tailscale`. [Tailscale Serve](https://tailscale.com/docs/reference/tailscale-cli/serve) provides HTTPS within the tailnet. Keep the host and local server running. Browser books and API keys are separate on each device and origin, including when switching from localhost to HTTPS. Export a `.chaya.pdf` and open it in the other browser to transfer a book and its saved work.

If the page says the app could not start, a content or ad blocker has probably blocked one of its files (the browser's console names it): allow the page in the blocker. File names that blockers match, such as "pageview" or "analytics", are avoided.

The app is static, so it can also be hosted anywhere (GitHub Pages and the like); `?book=` then needs a URL the browser may fetch.

## Books

A book is a folder of files (in the browser's storage, or inside its `.chaya.pdf`; the app cannot open a folder from disk, only a `.chaya.pdf`, a PDF or a URL). The PDF is the only input format (the user's decision, 2026-11-07): page images are to be made into a PDF first, for example with img2pdf.

```
book.json     {format: "book-folder", version: 1, book_id, title, types: "types.json", style: "style.json" (optional),
               pdf: {path: "source.pdf", name, sha256, page_count},
               pages: [{id, document, label, valid, pdf_page, width, height, image (optional), source}]}
source.pdf    the book's source PDF, exactly as given
types.json    the book's type list
style.json    optional: the book's style sheet (schema 0.3), named in book.json as style
pages/        one page document per page: the model's results, never changed by the editor
edits/        the user's corrected page documents, one per corrected page (no history)
work/         processing records, cached readings and structures, immutable API attempts, trial references and costs
images/       page images: a cache of pages drawn from the PDF (or, in the repository's folders, their rendered images)
```

`pages` lists the book's pages in reading order: for a book made in the app, every page of its PDF. A page that is not part of the book has a page document with no regions (above), not a separate list.

**Where a book lives:**
- **In the browser** (the usual place): the origin private file system, under `books/<name>/`, in any current browser. It is saved as you work. The address carries `?local=<name>`, so a reload reopens the book. The browser is asked for persistent storage (`navigator.storage.persist()`) when a book is made, imported or opened, and its answer is shown in the library and in Export. Storage can still be cleared, so a book worth keeping needs a copy on disk (below).
- **Read only** (only where the browser keeps no books, such as plain http): a `.chaya.pdf`, with corrections kept in IndexedDB.

**The copy on disk** (`js/disk-copy.js`, Chrome and Edge): Export's "Keep a copy on disk…", or the same button in the book's header, asks once for a file with `showSaveFilePicker`. Its handle is kept in IndexedDB, and the book is written to it as a `.chaya.pdf` when a processing run or comparison finishes or stops, after pages are moved on or sent back, and at most every five minutes while there are changes. Leaving the book writes its last changes first. Export can write it now, choose another file or stop keeping it.
- **The header** says when the copy was last written. Once the book holds a model result or an edit and has no copy on disk, it shows "No copy on disk" as a warning with "Keep a copy on disk…". Where the browser has no `showSaveFilePicker` (Safari, Firefox, phones), it offers "Download .chaya.pdf" instead, and the warning ends while a download has the latest change.
- **Permission:** after a reload the browser usually asks again before the app may write the file. The header then shows "The browser needs permission again…" with "Allow writing". A failed write is shown in the header with "Try again", and is retried with the next changes. Nothing is written when the book's files in the browser cannot all be read, so a damaged book never replaces a good copy.
- **Before spending:** a run that calls a paid model (stage processing, comparisons, page review, type proposals) waits in a dialog when no copy outside the browser has the book's latest change. The dialog offers to keep a copy on disk (or download one, or allow writing again), "Run anyway" or "Cancel". A working copy on disk never blocks a run, since it is written when the run ends.
- **A book whose files cannot be read:** opening a book in this browser first checks its source PDF and the document of every processed page (a page whose manifest entry has `valid` set). If any cannot be read, the book is not opened. The screen names each file and its error, and offers "Restore from the copy on disk", "Restore from a .chaya.pdf…" (the same book only), "Open what can be read" and the library.

**Page images:** a page is drawn from its PDF page, at exactly the `width` × `height` its regions are measured in, when it is first needed. A book in the browser keeps the drawing in `images/`; that cache is not part of the book's data. The size comes from the page's analysis when the book is made: a scanned page at 300 dpi, or the scan's own resolution when lower; any other page at 300 dpi. A page with an `image` file (the repository's folders) uses that file.

**A `.chaya.pdf`** (`js/chayapdf.js`) is the book as one file: its PDF with the book's data attached. The name is only a convention: the app recognizes a book's PDF by what is inside it, an attached `chaya.json` of format `chaya-book`, whatever the file is called.
- **What it holds:** the original PDF's bytes, unchanged, followed by one incremental update. The update attaches `chaya.json` (compressed, as an embedded file, also listed in the catalog's associated files).
- **chaya.json** is `{format: "chaya-book", version: 1, original: {name, sha256, length}, saved_at_utc, saved_by, files}`, where `files` holds the folder's files but `source.pdf` and `images/` (JSON files as objects, others as text).
- **Recovering the original:** a comment right after the original's bytes records their length and sha256, so the original is recovered exactly by cutting the file there, and checked.
- **No growth:** saving again rebuilds the update on the original, so the file does not grow.
- **The PDF's own attachments** are kept, in one flat list with `chaya.json`.
- **Viewers:** it opens as the book in any PDF viewer.
- **Encrypted PDFs** are refused.
- **Saving:** Export's "Save as .chaya.pdf" saves it once. In Chrome and Edge it saves into a chosen file; elsewhere it is a download. For a read-only book, "Save to … again" writes the same file again. A book in this browser keeps its copy on disk instead (above). Opening a `.chaya.pdf` and saving one both count as a copy outside the browser until the next change. Export also offers the source PDF alone.

**Edits:** an edited document keeps its `source` and adds `source.edited` (when, from which model result). A page whose corrections are all undone goes back to having no file in `edits/`. Versions that do not pass the checks yet are kept in the browser as drafts, and reopened with the page.

**Tools** (repository side):
- `tools/make_book_folder.py` makes a book folder from a transcription run (method 052, 054, 055 or the PDF methods' outputs). It upgrades 0.1 documents to 0.2 with `schema/inline.py`, gives each region its `box` from the region step's box, hard-links the page images, and hard-links the source PDF (`tools/add_source_pdf.py`, which also adds it to an existing folder).
- `tools/make_chaya_pdf.mjs FOLDER [OUT]` makes a folder's `.chaya.pdf`, reads it back and checks it. Each page entry gains its width and height, and drops its image.
- `tools/flag_counts.mjs BOOK.chaya.pdf [--pages]` counts the pages each stage flags, by flag kind, as the page grids do.
- **The books so far** are in `outputs/books/`, as folders and as `.chaya.pdf` files:

| Book | Folder | .chaya.pdf |

| Kale, all 252 pages (method 052, run `book-002`) | `kale-1913-book-002` | `kale-1913.chaya.pdf`, 15.6 MB |
| Telang, the 195 pages with text (methods 052 and 054) | `telang-dli-book-001` | `telang-dli.chaya.pdf`, 67 MB |

  The folders above and the private ones were checked against their `.chaya.pdf` on 2026-11-12 and hold exactly the same files; the `.chaya.pdf` is the book to open. `kale-1913-formatting-test`, `telang-dli-formatting-test` (method 055's formatting test) and `vachanamruta-059`, `-060`, `-061` (superseded by method 062) are older variants kept as folders only and are not openable in the app. A private book ("vachana", methods 056–062) is kept on the machine only, out of the repository.

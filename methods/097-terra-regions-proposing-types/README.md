# 097-terra-regions-proposing-types

Find regions that may also propose new unit types. The recipe is the default finder's, [method 042](../042-gpt-6.1-terra-none-book-types-continuations/) (GPT-6.1 Terra, reasoning off, the original page PNG at original detail, boxes as xyxy on a 0–1000 scale, the book's types with their region classes and continuation flags, strict structured output, 16,384 output tokens, store false) with the current local step ([094](../094-illumination-flattened-ink/README.md): outlines and line pieces from the page's ink). Two things change:

1. **Pending proposals are offered.** The request lists the book's pending proposed types (name, definition, region class, from `work/type-proposals/pending.json`) under "Proposed types, not yet accepted into the list", and their names are added to the region type enum. The list is read when the request is built, so a page sees what earlier pages of the same run proposed.
2. **New types may be proposed.** For a text unit that fits neither a listed type nor a pending proposal, the model gives the region type `other` and a `proposed_type` name, and defines that name once in `new_types` (name in the style of the book's names, one-line definition, region class). Marks that are not text units stay plain `other`.

Why: until now a region that fit no type could only be `other`, and new types came only from surveys. With this method, Find regions on individual pages both finds regions and adds unit types to the one pending list, so the type list grows from the pages a person is working on.

**The response stays schema-checked.** [response-schema-template.json](response-schema-template.json) is 042's schema with `proposed_type` (a string, empty for none) on each region and a `new_types` array; the app fills the type enum (listed types, `other`, pending names) and the region-class enum. The local check (`scaleProposingRegions` in `webapp/js/pipeline/proposing-finder.js`) runs 042's checks on every region and then: a region of a pending type, or `other` naming one, becomes `other` with that `proposed_type`; a name equal to a listed type (ignoring case and separators) becomes that type, with a warning; a new name keeps its definition, or an empty one with a warning when `new_types` lacks it; unused definitions are dropped with a warning. So a page never has a region of an unknown type: proposed-type regions are kept in `source.omitted_regions` with their `proposed_type`, drawn hatched, until the type is added.

**Into the pending list** (`recordFinderProposals` in `webapp/js/type-additions.js`): each new name becomes a pending `new_type` item whose source is the finder (method, run = the saved call, page, PDF page, regions); a name that matches a pending item from any source (case- and separator-insensitive) is merged into it, adding the page to its evidence and the spelling to its aliases; a name matching a dismissed item adds evidence there without reopening it; a name already added (or assigned to an existing type) adds nothing and its regions take that type. Recording the same result twice adds nothing. Only real runs record proposals; comparison trials do not.

**Review** is in the Regions tab's "Proposed types (N)" box (`webapp/js/proposals-view.js`). Adding a proposal (optionally renamed), or using an existing type for it, gives the type to every unassigned region carrying that name on pages nobody has edited or moved on, by rebuilding the page from its saved finder record (`Maker.assignProposedRegions`); pages a person protects are listed with links instead.

Settings: [config.json](config.json); prompt template: [prompt-template.txt](prompt-template.txt) (042's template with `<<PENDING>>`, `<<PENDING_TOO>>` and `<<CLASSES>>`); the runtime as run: [snapshot/](snapshot/) with [source hashes](source-sha256.json).

## How to run

In the app: Regions → Find regions → Change → "GPT-6.1 Terra · reasoning off · proposes new types". On the nine public references: `UV_CACHE_DIR=/private/tmp/scan-test-uv-cache UV_NO_SYNC=1 uv run --offline python methods/097-terra-regions-proposing-types/benchmark.py --run reference-002 --check` (remove `--check` to send the nine requests; the key comes from `OPENAI_API_KEY` or the llm key named openai). It runs [run.mjs](run.mjs) per page, scores with method 043's evaluator, and writes `comparison.json` beside 042's results under the same local step (094's regression-001).

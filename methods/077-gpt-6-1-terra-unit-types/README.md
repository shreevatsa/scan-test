# 077-gpt-6-1-terra-unit-types

GPT-6.1 Terra with reasoning off proposes a book-specific type list from up to twelve sample PDF pages. This is the initial unit-type step in the web app's new-book form. The user selects sample page positions and can preview the pages, inspect the proposal, edit descriptions and containment rules, and approve the list before creating the book.

The default sample includes the first three pages, an early page, two neighboring middle pages, a later page and the last page, deduplicated for short PDFs. Sample selection is editable. PDF.js renders page images as PNG at 150 dpi, capped at the scan's own resolution. The prompt uses the images, the book title and the user's description. It asks for semantic types, containers, printed region classes, flows, relations, inline kinds, transcription conventions, visible evidence by PDF page and questions for review. Hidden PDF text is omitted from the request. Settings are in [config.json](config.json), and the exact response contract is in [response-schema.json](response-schema.json).

The response uses arrays of named definitions, converted to the existing types.json format after checking duplicate names, sample-page citations, JSON Schema validity and the normal semantic type-list checks. The source identifies the model, method, PDF hash, sample positions and call record. Approval is recorded in the resulting type list. The user can also supply an existing type list, including when continuing from an excerpt of the same book.

The implementation is preserved in [snapshot/](snapshot/), with [source hashes](source-sha256.json). The request uses Responses with original image detail, strict JSON Schema, a 16,384-token output limit and store false. It follows the existing app transport and usage-based cost accounting. The structured-output contract follows the official OpenAI documentation. [Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

Each attempt receives a UUID and saves the image-free request, request hash, response, usage, cost and elapsed time through the app's call ledger. Before a book exists, these records are in IndexedDB under the source PDF's hash. Creating the book copies the records into its work files for .chaya.pdf export. IndexedDB ledger updates use one read/write transaction. A saved proposal can be restored when the same PDF is selected again.

Verification uses request and response fixtures, schema validation, pricing and ledger checks. Browser checks cover real PDF previews, the missing-key message, review controls using a saved fixture, invalid containment, approval and renaming with updated parent references. No live model request was made for this method during implementation because the browser has no configured API keys.

Live verification on 2026-11-09 UTC used the OpenAI key configured in llm and all four PDF pages of Cole's journal excerpt. The browser returned thirteen types in main and notes flows, with no schema or semantic type-list errors. The displayed estimated charge was $0.0200. The proposed types, review text, screenshot and report are in [cole-live-001](../../outputs/surveys/077-gpt-6-1-terra-unit-types/cole-live-001/). The proposal is pending human approval. The full response and usage are retained in the browser's source-PDF call record, identified by the saved type list's provenance.
